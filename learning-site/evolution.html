Self-Harness: Harnesses That Improve Themselves

手工调 harness 追不上模型迭代，于是把「改进」本身变成一个可审计的状态转移：失败签名、最小提案，再在没见过的题上回归。

  • B 论文精读
  • 3 步闭环
  • WU-4 正文

核心区别：不换模型、不引入更强的外部 Agent、不改模型参数——让被评估的那个模型，自己在当前 harness 下提出对 harness 的修改。固定模型 M、固定评估器 ℰ，只有 harness h 在变，所以任何涨跌都能归因到 harness。

三步闭环

先诊断，再开药，最后用没见过的题验药。三步对应论文里的 Weakness Mining、Harness Proposal、Proposal Validation。

  1. 01 / 3

    轨迹采集

    Weakness Mining

    在 held-in 上跑任务，收集轨迹、输出与判定；按失败签名 (c, q, m) 聚类，输出只描述病因、不规定改法的证据包。

  2. 02 / 3

    弱点提案

    Harness Proposal

    同一个固定模型以 proposer 身份，提出 K 个「多样但最小」的改动；每个绑定一个失败机制和一个可编辑面，并附审计记录。

  3. 03 / 3

    回归采纳

    Proposal Validation

    每个提案都当作新的 harness 变体，在 held-in 与 held-out 上重跑；两边都不降、至少一边升，才合入下一版。

↺

闭环：通过的提案合入 ht+1，下一轮从新的 harness 继续；被拒绝的只记日志，不改当前状态。改进不是一次分数，而是一条有据可查的版本链。

失败签名不是「超时」这种粗标签，而是三元组：验证器拒绝的终端原因、轨迹里导致失败的因果状态、以及可复用的 agent 机制。三项都一致才进同一个簇——评估者负责诊断，提议者负责开药，两者不混。

held-in / held-out：两边都不降

每个提案都在同一个评估器下重跑两套题，接受规则非常保守。

held-in

见过的题

提议者看过失败证据的那部分任务。用来检验：它是否真的解决了被指出的问题。

held-out

没见过的题

提议者从未见过的任务。用来检验：它有没有为了修 A 而弄坏 B。

Δin ≥ 0 且 Δho ≥ 0 且 max(Δin, Δho) > 0

为什么不用总分：总分会把「拆东墙补西墙」藏起来。一个改动可能让 held-in 涨 5 个点、held-out 掉 4 个点，总分仍然是正的，但它很可能只是背下了已见过的失败。

held-out 怎么防自欺：它把「记住答案」和「学会方法」分开——只有在没见过的题上也不退步，才说明改动是泛化的，而不是对证据的过拟合。评估有随机性时，还要重复跑、按聚合通过数应用同一规则，降低一次好运被采纳的概率。

可审计：每次 ht → ht+1 都留下记录：改了什么面、针对哪个失败模式、预期效果、回归风险、两边涨跌、重复次数、采纳还是拒绝。

术语表

轨迹trajectory τ
一次任务执行中模型的动作、工具调用、观察和中间产物的完整记录；失败签名从轨迹里提取。
提案proposal
对 harness 的一个最小、可审计的改动，绑定具体失败机制和可编辑面。
held-in
提议者看过失败证据的任务集合，用来确认改动确实解决了动机证据。
held-out
提议者没见过的任务集合，用来确认改动没有为了修 A 而弄坏 B。
