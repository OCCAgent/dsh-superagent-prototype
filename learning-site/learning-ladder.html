学习阶梯 · 5 级

五级台阶，把 Super-agent 学到能改

把「学 Super-agent」拆成五级：完全新手、基础理解、实际使用者、问题解决者、自信实践者。每级八项、一个里程碑、一个自检问题；过不了就停在原地补，不靠「看过」升级。

  • 5 级 × 8 项
  • 5 个里程碑
  • 方法来自 Rahul (@sairahul1)
方法来源：五级与八项的结构来自 Rahul（@sairahul1）的文章 How To Learn Anything 10x Faster Using Claude（2026-06-20）。原文用这套结构向 Claude 学任何主题；本页把「主题」换成 dsh-superagent，把每级的事实锚定到本仓库的文档、源码与实验记录。这是一条学习路线，不是学习者实验：没有测过它能把学习速度提高多少。

为什么收藏不等于学会

原文的判断很直接：随机提问会得到随机答案，当时觉得懂了，一周后什么都不剩。真正的学习需要四样东西，而普通 AI 对话常常四样都缺。

  • 路径先学什么、后学什么，不跳地基。
  • 测试在付出代价之前，先知道自己哪里不会。
  • 压缩把知识压到能在 5 分钟内复习。
  • 反馈缺口马上被发现并补上，而不是悄悄堆积。

这条阶梯负责「路径」和「测试」：每级的八项里已经埋了练习、里程碑和自检。压缩与反馈放在后面：一页速查和费曼回路。

三条使用规则

1先定位，再开走

用下面的总览表自评。不确定自己在哪级，就从 L1 的自检题开始；答得顺，再往上试。

2通关 = 里程碑 + 自检 + 一个失败路径

里程碑要拿得出东西；自检要答得上；还要能说清「这一步失败会怎样」。三样缺一，留在本级。

3不按时间升级

每级标的时间只是投入参考，不是资格。卡住时把问题按 problems.md 的六字段写下来，再回上一级找缺口。

五级总览

左边是级，右边是原文的难度名。最后一列是升级的凭据：一个交得出来的里程碑；再配合每级第 8 项的自检。

级原文对应一句话过关里程碑
L1Complete Beginner能判断「该不该交给它」150 字外行版 + 答住 3 个追问
L2Basic Understanding能把系统当状态机读白纸画出主链路、两条旁路与三个失败点
L3Practical User能独立走完一次真实闭环一次小改动从触发到 PR，并逐阶段对上面板
L4Problem Solver能从症状定位到记录一份可被他人复现的故障记录
L5Confident Practitioner能改一层并证明没弄坏一页 RFC 过评审十问，或一个小实现 + 回归

五级台阶

每级按原文的八项展开：01 级别名、02 要理解什么、03 掌握的表现、04 重点概念、05 过关里程碑、06 动手练习、07 常见错误、08 自检问题。先读 02–05，再去做 06；08 的答案折叠在下面，先自己答。

L1

01 · 级别名

完全新手 Complete Beginner

你不需要会写代码，只要能判断「这件事该不该交给它」。

约 2–4 小时
02 · 这一级要理解什么

它不是模型，也不是「多 Agent 框架」。它是一个对一个 GitHub 仓库干活的主动 Agent：在飞书或 GitHub 收到请求，判断是否被授权，再把工作放进独立工单执行。

一条请求的旅程：消息先成为 Trigger；Eval 判断要不要接；接了才建 Ticket 和不可变的 Mandate；Assignment 把工单交给 Executor；做完用 Report 和原渠道回复。

两层分工是结构约束，不是提示词：Main Session（Router）只判断和派活，不干具体活；Executor（Worker）在自己的 Session 和目录里干活，只向工单汇报。

四个特征——连续、产出、主动、持久——不是口号，分别对应「跨渠道同一身份」「并行不堵」「环境事件能触发」「重启能恢复」。

03 · 掌握的表现
  • 用 3 分钟讲给不写代码的人，不用 Router/Worker 也能讲清谁在什么时候做什么。
  • 能说出它和「给聊天机器人接一堆工具」的区别：先授权、有工单、有审计、有回滚边界。
  • 能举出一个「它不该做」的例子，并说明该由谁做，例如没人授权、超出范围、合并 PR。
04 · 最重要的概念与技能
  • Source / Trigger / Ticket / Executor / Mandate：先要直觉，不背定义
  • 四个特征：连续、产出、主动、持久
  • 两条边界：PR 出现 ≠ 可合并；工单结束 ≠ 授权被撤回
05 · 过关里程碑

写一段 150 字以内的大白话说明，并让一个不熟悉这套系统的人追问 3 个问题；你能当场答上。说明和问题记进自己的笔记，不需要公开。

证据：150 字说明 + 3 个追问的答案。

06 · 动手练习

打开面板 Overview 和仓库 README，找一张真实工单（例如本页所在工单），写下四个答案：谁提的？授权范围是什么？谁在执行？结果回到哪里？

再去概念页对照四特征，各写一句「它在这张工单里体现在哪」。

07 · 常见错误
  • 当成「更聪明的聊天窗口」：忽略授权、工单和审计。
  • 以为 Agent 越多越好：这里的关键恰恰是 Router 不执行、Worker 隔离。
  • 一上来读源码：L1 读源码只会记住名词，画不出流程。
08 · 自检问题

同一个人在同一个 Thread 里把同一句话发两遍，会不会建两个工单？为什么？

参考答案

不会。Trigger 是幂等单位：同一个 Trigger 被 accept 两次也只建一个 Ticket。新消息若落在已订阅的 Thread 上，会作为上下文扇出给工单，由它的 Worker 判断是否属于本工单；只有超出工单范围、被 handback 的消息才重新进入 Eval。判据不是「发了几次」，而是同一条 Trigger 和同一个 Thread 的归属。

L2

01 · 级别名

基础理解 Basic Understanding

把系统当成状态机读，而不是一串功能名。

约 6–8 小时
02 · 这一级要理解什么

主链路：Source → Trigger → Thread → Eval（Gate + Assessment）→ Decision → Ticket（带 Mandate）→ Assignment → Executor → Report → Channel。

两条旁路：Subscription fan-out 只把 Thread 上的新消息送进工单当上下文，不授予权限；Correlation 只补上下文，从不路由。

Ticket 的七个阶段按「在等谁」定义：person/delivery、person/answer、person/review、person/blocked 或 failed、working/queued、idle、working。读表从上到下，第一条命中就是当前阶段。

恢复不是「重启一下」：delivery 有退避重试，blocked/failed 由人的消息释放，Assignment 中断带恢复注记，prepare 失败要重试或人的新消息才会再准备。

03 · 掌握的表现
  • 白纸画出主链路，任指一个节点，能说出输入、输出和失败后的去向。
  • 能解释 accept、stop、ignore、unavailable 四种 Decision 分别意味着什么。
  • 能解释为什么工单结束不等于授权撤回，以及什么情况下授权才失效。
  • 能区分「进了工单上下文」和「创造了新工作」。
04 · 最重要的概念与技能
  • Gate（确定性准入）vs Assessment（模型研判）
  • Mandate（不可变授权）与 Policy version
  • Subscription、fan-out 与 Correlation
  • Disposition、Decision、Report
  • Ticket 的七个阶段
05 · 过关里程碑

用一张 A4 画出主链路、两条旁路和三个失败点；用 5 分钟讲给一个同伴。对方随机指一个节点，你能说出它失败后去哪、由谁推进。

证据：手绘图（照片或文字版）+ 一次讲解。图中的节点必须来自面板里的真实记录。

06 · 动手练习

在面板的 Trigger、Eval、Execution 各找一条记录，按「Disposition → Decision → Ticket → Assignment → Report」抄成一条链，并标注每一步是代码还是模型做的。

再回到 docs/001-domain.md 和 docs/005-panel.md 核对术语，把叫错的词改过来。

07 · 常见错误
  • 把 Eval 当执行器：Eval 只判断，不干活。
  • 把订阅当授权：扇出只加 context，Mandate 才能授权。
  • 以为 Ticket 跟着 Session 走：Ticket 有自己的 open/ended，可以换 Executor。
  • 以为工单结束就收回授权：只有人 stop 或 Policy 不再持有才撤回。
08 · 自检问题

一条群里的普通讨论，为什么可能进入某个工单的上下文，却不能自己变成新任务？

参考答案

因为它所在的 Thread 可能被工单订阅，消息会被扇出成 Input；但没有经过 Eval 的 accept，就不产生 Mandate，也不会建 Ticket。上下文和授权是两条线。

工单从 blocked 回到 working，通常需要什么？

参考答案

人在它的 Thread 上发消息，或者重试 delivery。blocked/failed 时系统不自动投递 CI 和机器人消息；人的消息会解除这个 hold。

L3

01 · 级别名

实际使用者 Practical User

能把它当工具用，独立走完一次真实闭环。

约 8–12 小时
02 · 这一级要理解什么

起服务：一个独立的 DSH profile、面板、Source（GitHub，可选飞书）、Policy 允许名单、Executor 目录与 prepare 命令。

提请求：在原渠道写清目标、范围、验收；explicit 是明确请求，inferred 只能走已匹配的规则，范围更窄。

看状态：Overview 先看「需要我」，再看工单阶段；Trigger 页看 Disposition 与 Decision；Execution 页看 Assignment 与 Report。

交付边界：ready 的 PR 只是「等人看」；默认由人合并，Agent 不代替评审，也不把「PR 已开」当成完成。

03 · 掌握的表现
  • 独立完成一次小改动闭环（文档、测试或单函数），并能对照面板说出每个阶段为什么停。
  • 能判断一条请求该走 explicit 还是 proactive 规则；能写出 100 字以内的验收标准。
  • 能读懂 ready、blocked、waiting 三种 Report 的差别，并知道下一步该谁动。
  • 知道什么时候该在同一 Thread 追问，什么时候该另开一条消息。
04 · 最重要的概念与技能
  • 部署与配置：profile、Source、Policy、Executor、prepare
  • 请求写法：目标、范围、验收
  • 面板：Overview、Trigger、Eval、Execution、Settings
  • Report 语义：progress、waiting、ready、blocked、failed、dropped
05 · 过关里程碑

一次真实小改动从触发走到 PR，且你能对照面板复述每个阶段；PR 由人 review/合并，或在记录里明确写出「尚未合并、原因是什么」。

证据：脱敏后的 Trigger id、Ticket id、Report 阶段和 PR 链接。

06 · 动手练习

在一个测试仓库提一个「只改一个文件」的请求。记录 Trigger id、Decision、Ticket id、Assignment、Report 和 PR 链接。

然后故意在同一 Thread 追问一句，观察它是继续同一工单还是新建。把两次路径画出来，和 L2 的图对照。

07 · 常见错误
  • 需求太宽（「重构一下」）：范围失控，或者被暂停。
  • 没写验收：PR 开了但不可用。
  • 把 PR 出现当成完成：ready 只是等人 review。
  • 替 Agent 批准或合并：越过评审边界。
08 · 自检问题

一个 ready 的 PR 出现后，工单处于哪个阶段？下一步谁做什么？

参考答案

通常是 person/review（面板显示「等待审阅」）。下一步是人 review 并决定合并；默认没有配置合并 CLI 时由人合并，Agent 不会代人批准，也不会直接合并。只有交付要求明确指定合并 CLI 且条件满足时，它才会启用 auto-merge。合并或关闭后，工单才按 PR 结果结束。

同一 Thread 的追问，和另开一条新消息，路径差在哪？

参考答案

同一 Thread 若已被工单订阅，追问直接扇出成 Input，不进 Eval；另一条新 Thread 没有订阅，要走 Source → Eval 才会成为新工作。

L4

01 · 级别名

问题解决者 Problem Solver

从「它怎么不动了」走到「证据在哪、下一步验证什么」。

约 10–15 小时
02 · 这一级要理解什么

先分层再查记录：没收到（Source 没监听、被 Source 层过滤）→ 收到没建单（允许名单与 Gate、Assessment、Decision）→ 建单没跑（Assignment、prepare、槽位）→ 跑了没回（delivery、Channel、outbox）→ 回了但不对（scope、prompt、model）。

四类记录：Disposition（去哪了）、Decision（为什么）、Assignment（谁在跑）、Report（跑到哪）。再加系统问题、outbox 失败和恢复注记。

恢复机制要背下来：delivery 从 2 秒起、指数退避到 1 分钟；Channel 从 5 秒起、退避到 300 秒；worker 的 turn 结束后后台工作最多 30 分钟；prepare 失败不会自动重试；restart 用恢复注记让 worker 先核对目录、git 和 GitHub。

「先取证，后重启」：restart 会结束运行中的 Assignment，现场可能就没了。

03 · 掌握的表现
  • 给定「没回复、没建单、卡住、结果不对」四类症状，先给假设，再查对应记录，不先重启。
  • 能区分 Policy 过滤、模型 ignore、执行失败、投递失败，而不是统称「Agent 坏了」。
  • 能用测试或最小案例复现，而不是只读日志。
  • 修复后能写出「改了什么、没改什么、为什么」，并留下可复查的证据。
04 · 最重要的概念与技能
  • 症状到层的映射
  • Disposition、Decision、Assignment、Report
  • retry、restart、hold、recovery note
  • 并发与槽位、后台工作 30 分钟上限
  • 关键源码：src/policy.ts、src/app/assessment.ts、src/core/stage.ts、src/core/tickets.ts、src/core/intake.ts、src/executor/dsh.ts
05 · 过关里程碑

选一个真实或构造的故障，写下「症状 → 假设 → 检查 → 结论 → 修复或不修的理由」，并让另一个人只按这份记录复现一次。复现成功，才算过关。

证据：故障记录 + 复现命令或报告。

06 · 动手练习

从 problems.md 选一条（PR base 冲突、沙箱凭据、流中断、部署落后、pnpm 超时），复现或构造最小案例。

或者跑一次 pnpm test 或 python3 learning-site/shot.py，人为制造一个失败，按报告定位到具体检查项，记录命令、输出和结论。

07 · 常见错误
  • 先重启后取证：现场没了。
  • 把 Policy 过滤当 bug：允许名单与准入本来就会挡。
  • 看日志没有假设：越看越乱。
  • 用 Policy 修执行层的 bug：授权层不该背执行层的锅。
  • 把「PR 已开」当「工单完成」。
08 · 自检问题

一条飞书消息既没有回复，也没有工单记录，你先看哪三处？

参考答案

① Source 是否在监听、是否被 Source 层过滤（Disposition）；② 是否入库并进入 Eval，Decision 是 ignore 还是 unavailable；③ 是否有 Ticket/Assignment，以及 delivery 是否失败。三处分别对应「没收到」「收到没接」「接了没送达」。

working/queued 与 idle 的区别？

参考答案

queued 是还没有 Assignment 或 Assignment 仍是 pending，或者在等空闲槽位；idle 是这一轮已经结束（Report waiting 或 Assignment ended），在等下一个 Trigger。前者等资源，后者等输入。

L5

01 · 级别名

自信实践者 Confident Practitioner

能判断该改哪一层，并证明改动没有把系统弄坏。

约 15–20 小时
02 · 这一级要理解什么

四种改动面：Prompt/Policy（团队可编辑）、Source/Channel（部署实现）、Executor/domain（代码）、架构（跨模块）。改错层，越努力越糟。

每个改动都要过六问：失败场景是什么？权限怎么变？怎么回滚？怎么观测？成本多少？对已有调用方和数据怎么兼容？

已知的架构缺口：没有显式引用的跨 Thread 归属（实验里的 C4），以及没有独立控制环的 Watchdog。这两件事都不是 prompt 能修的。

验证要分 held-in 与 held-out：先证明它解决了 motivating evidence，再证明没把没见过的场景弄坏。

03 · 掌握的表现
  • 能写一页 RFC：问题证据、候选方案、权限影响、失败模式、回滚、观测指标、验证计划。
  • 能指出一个改动会破坏哪条现有保证，例如「Router 不执行」「订阅不授权」。
  • 能设计 held-out 用例，而不是只跑自己调参用的那几条。
  • 能在改 prompt、改配置、改代码、改架构之间做出有理由的选择。
04 · 最重要的概念与技能
  • Source/Channel 的接口、幂等键、读位置
  • Policy 版本、Mandate 重校验、准入表
  • held-in / held-out 回归
  • 迁移、兼容、灰度、回滚
  • 评审十问与失败注入
05 · 过关里程碑

写一页 RFC，或实现一个小 Source/Channel。RFC 要能通过评审十问，至少三个失败场景有明确处置，含回滚与观测；实现要有测试、迁移说明和一次失败注入的结果。

证据：RFC 链接或 PR + 评审记录 + 验证结果。

06 · 动手练习

给「跨 Thread 自动归属」写一页 RFC：先用 C4 的证据说明问题，再比较「语义匹配」与「来源业务键」两条路，写清权限影响、误归属的代价、回滚和指标，最后用评审十问自检。

或者设计一个只读 Source，定义事件、幂等键、读位置、身份和失败处理，并补一组测试。

07 · 常见错误
  • 用 prompt 修结构缺口：改的是话术，不是机制。
  • 新 Source 没有幂等键或读位置：重启就重放。
  • 给自动合并权却没有 held-out 回归：把评审风险自动化了。
  • 只在调参用例上验证：过拟合。
  • 没有回滚和观测就上线：出事只能猜。
08 · 自检问题

给系统加一个新 Source，至少要在哪三处定义身份、幂等和读位置？

参考答案

① Source 实现：什么算一个事件，actor、thread、channel 怎么翻译；② Policy：这个 Source 的允许名单、同步与准入；③ 领域层：Trigger 的幂等键、Source 的读位置。缺一处就会重复、越权或重放。

为什么 Watchdog 不能只是主 Session 里的一段 prompt？

参考答案

因为主 Session 就是被监控对象；它卡死时，同一循环里的 prompt 也停了。独立控制环需要独立进程、预算、凭据和审计，才能在主系统失效时仍然工作。

L5 的评审十问

L5 的里程碑要求「通过评审十问」。这十问不是形式，而是把 RFC 从「想法」变成「可评审的改动」的最低标准。

#问题它在防什么
1问题证据是什么？不改会怎样？为想象中的问题写代码
2改的是哪一层：prompt、配置、代码还是架构？用最贵或最错的一层解决问题
3最坏的失败场景是什么？影响多大？只写 happy path
4权限边界变了吗？谁能触发、范围多大？悄悄扩大授权面
5误判或误归属的代价是什么？怎么发现和纠正？把错误自动化
6怎么回滚？回滚会丢什么？做出一张单程票
7怎么观测成功和失败？指标、日志、告警在哪？上线后只能靠猜
8成本增加多少：token、延迟、槽位、人工？用无限预算换一点收益
9对已有 Source、Ticket、数据怎么兼容或迁移？破坏现有调用方
10held-out 用例是什么？怎么证明没把别处弄坏？只在调参用例上过拟合

五个「假掌握」信号

以下任何一条成立，说明还停在前一级，不是「学得差不多了」。

能背四特征，说不出一次失败的恢复路径。记住的是词，不是状态机。
能画正常流程，说不清 blocked → working。没理解谁有权推进它。
能读源码，给一个负载说不出先崩哪。还没有量级感。
能开 PR，写不出验收标准。还没到 L3。
能改 prompt，分不清授权层和执行层。还没到 L5。

费曼回路：把「懂了」变成「讲得清」

原文的费曼回路只有三步：先讲给一个 12 岁的人听，再让对方复述或追问，最后只补他卡住的地方。它专门抓「假掌握」：你以为自己懂了，一开口就露出缺口。

在这套主题上，最好的人选是一个不写代码但会用 GitHub 的同事。你讲 L1 的定义，他问「那它和 Copilot 有什么区别」；你讲 L3 的 ready，他问「那谁点合并」。每个问题都指向一级的具体缺口。

1讲一遍

不用术语，3 分钟内讲清「它是什么、一次工作怎么走完」。

2让对方复述

他讲错的地方，就是你的缺口；不要替他补。

3只补缺口

回到对应页或源码，补完再讲一遍，直到他能转述。

卡住时：概念缺口回概念页，进化缺口回进化页，实现缺口回原型页，证据缺口回测试日志和实验全记录。问题本身按 problems.md 的六字段记下来。
