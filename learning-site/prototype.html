原型 · 论文到实现

论文给骨架，原型补边界

论文回答「怎么组织」；原型回答「一次被授权的工作，怎么安全做完并留下证据」。下面是对照、七个阶段、三处偏离，以及缺失的 Watchdog。

  • 概念对照
  • 7 个阶段
  • L1–L5 掌握路线

先校准：原型不是论文的逐条实现。仓库 README 明确说它经过改编，不等同论文或内部版本；下面的对应是概念对应，不是代码等价。

概念映射：论文的词，落到哪里

论文概念原型概念差异要点
RouterMain Session（orchestrator）+ Eval判断拆成 Gate（确定性）与 Assessment（模型）两层；Eval 无状态。
WorkerExecutor Session（worker-<ticket-id>）不只隔离上下文，还有独立目录、执行环境与 worker 槽位。
会话Ticket工单有自己的生命周期，不跟随 Session。
任务派发Assignment工单与执行器实例的绑定，可多次、可替换。
透传Subscription fan-out扇出到 Ticket 的 Input；不过 Gate、不授予新权限，但仍经领域层，因此可审计。
过滤Gate + AssessmentGate 是白名单、规则与强度；Assessment 才是模型研判。
触发Trigger + Disposition每个 Trigger 的去向（filtered / evaluated / fanned out）都被记录。
—Policy / Mandate论文几乎没展开的授权层：谁、以什么强度、多大范围。
—Channel / CorrelationChannel 是写回；Correlation 只加上下文，从不路由。
—Disposition每个 Trigger 的去向（filtered / evaluated / fanned out）都被记录，是审计与排查的入口。
WatchdogHealthBoard + 重试 + 恢复注记自愈更像确定性流程，没有与论文对应的独立 Agent 控制环。

三处偏离：原型比论文多做了什么

授权前移

论文问「这条消息要不要处理」；原型的 Gate 先问「谁、在哪个来源、以什么强度、授权了多大范围」，再生成不可变的 Mandate。执行只问「在不在范围内」。

审计成为数据

Trigger 有 Disposition，判断有 Decision，工单有 Assignment 与 Report，消息有 outbox 记录。于是「为什么这条没回」「为什么这个工单停了」都能查。

状态自持

工单不跟随 Session：它可以被交接、恢复、换执行器，所以定义自己的七个阶段。代价是概念更多，收益是可授权、可审计、可恢复。

一句话：论文回答「怎么组织」，原型回答「一次被授权的工作，怎么安全地做完并留下证据」。

七个阶段与两条恢复路径

工单不是「跑着 / 没跑」两种状态，而是七种，取决于它在等什么。判断从上往下，第一条命中即止。

阶段条件面板显示
person / delivery投递 Input 失败，正在退避重试输入未送达
person / answer有一个待回答的 Attention等待回答
person / review最新 Report 是 ready等待审阅
person / blocked、failed最新 Report 是 blocked/failed，且之后没有人再说话受阻 / 失败
working / queued没有 Assignment，或 Assignment 还在 pending排队中
idle最新 Report 是 waiting，或 Assignment 已结束等待触发
working其余执行中

retry：人的决定

结束当前 Assignment，在同一 Session、目录、分支、PR 上起一个新的。它假设执行现场还在，只是这一轮没跑好。

restart：宿主的事实

所有运行中的 Assignment 统一以 host restarted 结束；新 Assignment 带恢复注记：先查目录、git 历史、GitHub，确认哪些外部动作已经做过，再决定是否重复。

别混为一谈：把 retry 当 restart，恢复时会重复外部动作；把 restart 当 retry，会以为现场还活着。

缺失的控制环：Watchdog

原型有健康看板、失败重试、恢复注记、七种阶段，但没有论文里那个独立 Agent 控制环。缺的不是监控，是任务级进展判断和分级干预权限。

死会话或进程没了，工单停在半路。
卡活着，但长时间没有实质产出。
飘有产出，但偏离授权范围或目标。
假声称完成，产物缺失或不可用。

不能直接照抄论文：每个活跃工单都让模型定期看一眼，成本随并发线性涨；长编译、大重构、等 CI 都像「没进展」；Watchdog 要读工单内容，而工单内容是不可信输入。稳的做法是用论文自己的快慢路径原则来补它。

  1. 进度账本只有代码提交、产物变化、验证结果、外部事件、报告迁移、交付成功算进展；心跳、日志、回复都不算。每个阶段的预算不同，长任务要显式声明「我预计 40 分钟编译」。
  2. 规则筛可疑快路径十条规则：无进展、同一错误重复、ready 但产物不存在、槽位超限、投递失败、空转、危险命令、反复回退、成本燃烧等。规则只产出「可疑」，不产出结论。
  3. 模型裁决只对可疑工单，输入有界证据包（Mandate、时间线、触发的规则、当前阶段、Worker 原话）。输出结构化裁决：classification、confidence、hypothesis、evidence、recommended_action；必须给证据。
  4. 权限阶梯L0 影子 → L1 通知 → L2 提醒 → L3 暂停 → L4 重派/回滚（不建议自动）。每一级都要有可统计的成功率与误伤率，晋升看记录，不看愿望。
  5. 安全边界独立进程、独立预算、独立凭据；它读的内容一律当不可信输入，防注入；可逆优先，先通知再提醒再暂停；它自己也要有心跳、死手开关和动作审计。

上线节奏：先影子运行，再红队测试，最后才给有限权限。监控者本身也是一个需要被监控的系统。

掌握路线：L1–L5

「完全掌握」需要一个可检验的定义。每级都有通过标准，不达标就停在原地补。

  1. L1 复述不看文档，用 10 分钟讲清：为什么 Router 不干活、四关各解决什么、为什么透传不提升速度、为什么存算要分离。外行能听懂，被追问「不做会怎样」时能给出具体后果。
  2. L2 画图手画 Source → Trigger → Thread → Eval → Decision → Ticket → Assignment → Report → Channel；标出七个阶段、三个失败点、两条恢复路径。随便指一个节点，能说出输入、输出和失败后的去向。
  3. L3 定位找到 Gate（src/policy.ts）、Assessment（src/app/assessment.ts）、Ticket 阶段（src/core/stage.ts）、worker 槽位（src/executor/dsh.ts）、扇出与工单生命周期（src/core/tickets.ts、src/core/intake.ts）；查一条 Trigger 的 Disposition → Decision → Ticket → Assignment，自己推阶段再和面板对照。
  4. L4 预测给定负载（如 60 条/分钟）或故障（Router 重启、端点离线、重复投递），预测先崩哪里、用户看到什么；预测与实测一致，或差异能解释。
  5. L5 改造设计一个新 Source/Channel、Router 分片方案，或补上 Watchdog；写清失败场景、权限与回滚。方案能通过「如果我是评审会问的十个问题」，至少三个失败场景有明确处理。

四个「假掌握」信号

能背名词，画不出失败路径。记住的是术语，不是状态机。
能画正常流程，说不清 blocked → working。没理解「谁有权限推进它」。
能读代码，预测不了 60 条/分钟先崩哪。还没有量级感。
能改代码，写不出验收标准。还没到 L5。
