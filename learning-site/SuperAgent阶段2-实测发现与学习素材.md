## 一、实测发现（按价值排序）

### F1 · 被判定「重复/无新工作」的消息不会得到群内回执

- **现象**：用户补发 WU-3（12:53:05Z，@OCCLab）后群里无任何反应，观感"被无视"。
- **真相**：消息被完整处理——trigger 入库 → Router 新建 worker（`adc1230c`）→ Worker 检查 git 历史/工作区/PR 状态 → 发现 WU-3（PR #5）已于 12:45:15 合并（早于补发 8 分钟）→ 判定 `dropped / Duplicate request`，**不重复开 PR**（遵守"一个 WU 一个 PR、不重复已完成工作"纪律）。
- **缺口**：`dropped` 判定默认只在状态库/report 留痕，**不产生群内可见回复**。
- **启示**：
  - 任务已被接住但"无事可做"时，SuperAgent 选择沉默而非解释——使用者应知悉这一行为；
  - 若希望得到可见回执，可在任务里显式要求"如判定无需执行，请回复原因"。

### F2 · PR 合并会终止当前 worker assignment（连续派发的丢单风险）

- **现象**：WU-2、WU-3 连续派发（间隔 43 秒，P1 并行场景）。WU-2 的 PR #4 被用户合并时（12:31:35Z），正在同一 worker 上下文里的 WU-3 随之中断——worker `e1e572a8` 结束（endedAt = PR #4 合并时刻），WU-3 当时尚未开出 PR。
- **机制**：worker assignment 的生命周期与它产出的 PR 合并事件联动；PR 合并 → assignment 结束 → 该 worker 尚未完成的后续单元消息丢失（不自动重投）。
- **结果**：WU-3 后被处理 WU-4/5/6 的 worker 自主补齐（PR #5），未造成永久缺失——**但这属于"幸运的自动补偿"，不是机制保证**。
- **启示**：
  - 连续派发多个单元时，若前一个单元的 PR 已合并，后一单元应**重新确认或等待新回执**，不要假设它还在同一 worker 手里；
  - 重要单元的交付状态以 **PR 是否出现** 为准，不以"收到回执"为准。

### F3 · 不 @ 的消息也会入库 trigger，但过滤发生在下一层（A2 判据修正）

- **现象**：用户发不 @ 的消息（"进度如何" 12:21:53Z、"学习网站的学习计划是什么" 12:35:35Z），trigger 表**均有记录**——与测试方案 4.3 A2 判据"不产生 trigger"不符（该判据已于 2026-11-05 修正为“不产生 decision/工单”；trigger 仍可入库作上下文）。
- **真相**：当前飞书 Source 配置 `admission: {}`（无 mention-only 过滤），拉取群全量消息。两级过滤的第一级实际发生在 **disposition/Eval 层**：
  - @ 消息 → Eval 判定（decision）→ 路由/建工单；
  - 非 @ 消息 → **跳过 Eval（无 evalId）** → 直接 fanout 为当前 Thread 工单的上下文消息（不建新工单、不打断执行）。
- **修正判据**：A2 应改为"不产生新 decision、不建新工单（仅作 Thread 上下文）"。
- **启示**：群里的非 @ 消息会被 worker 看到（作为上下文），适合补充背景、问进度；要**触发新任务必须 @**。

### F4 · Worker 具备「识别重复、拒绝无效工作」的自主判断力

- **现象**：补发 WU-3 的 worker 报告明确写明："Duplicate request, no new work: the re-sent WU-3 was already delivered and merged… I re-checked the worktree, git history and PR state and made no changes and no duplicate PR, per one-PR-per-WU and do-not-repeat-completed-work. WU-4/5/6 are still pending."
- **解读**：Worker 不仅执行，还会**核实前置事实**（git 历史、PR 状态）再决策，并遵守任务级纪律（一个 WU 一个 PR）。这是"主动"特征在真实任务里的体现。
- **启示**：任务描述中写明纪律（如"不要重复已完成工作"）会被 Worker 尊重并执行。

### F5 · 同 Thread 后续消息「插话直通」，不碎片化建单（P2 机制实测）

- **现象**：WU-1（11:56）、WU-2（12:20）、WU-3（12:21）、术语表插话（12:34）落在同一飞书 Thread，全部追加进**同一个总纲工单**（`8f6f1d62f6dc`）的 inputs，由 Router 依次指派 worker，**未产生多个碎片工单**。
- **机制**：Trigger 按 Thread 聚合 → 追加为工单 inputs → worker 逐个读取（readAt 可查）。插话消息（"WU-4 加一节术语表"）被对应 worker 正确并入当前任务（ack 明确"与三步闭环、回归规则同一 PR 交付，不重启任务"）。
- **启示**：同一项目的多个 WU 在同一群聊/同一话题下连续下发是安全的——上下文会连贯进同一工单；想开"平行任务"才需要换渠道/换话题。

## 二、学习要点（如何更好地使用 SuperAgent）

| 场景 | 正确姿势 | 错误姿势 |
|---|---|---|
| 确认任务被接住 | 看 trigger 入库 + 等待 ack/PR；dropped 无回执是正常的 | 只凭"群里有反应"判断 |
| 连续派发多个单元 | 逐条下发；每个单元以 PR 出现为准；若某单元长时间无 PR，补发一条 | 假设所有单元在同一 worker 手里自动串行完成 |
| 补充背景/问进度 | 群聊不 @ 直接发（会作为上下文进入工单） | 不 @ 却期待它触发新任务 |
| 触发新任务 | 必须真 @（名字变蓝） | 手打文本 @（不算 mention） |
| 修改进行中任务 | 同 Thread @ 追加要求（插话直通） | 另开话题/换渠道（上下文断裂） |
| 避免重复工作 | 任务里写明"已完成的不要重做" | 重复下发已完成单元（会 dropped 且无回执） |
